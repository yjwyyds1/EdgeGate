# EdgeGate 性能基准

## 测试环境

| 项 | 值 |
| --- | --- |
| 主机 | Intel i5-12500H，WSL2 |
| 虚拟 CPU | 4 |
| 内核 | 6.18.33.1-microsoft-standard-WSL2 |
| 编译器 | GCC 15.2.0 |
| CMake | 4.2.3 |
| 构建 | Release（`-O3 -DNDEBUG`） |
| 网络 | loopback |
| 绑核 | 未绑核；存在 WSL 调度抖动 |

**数字只对本环境、本负载、本构建有效。** 不同 CPU、内核、WSL 版本和是否绑核都会改变结果。

## 方法

- 3 个 `eg_demo` 实例（9001/9002/9003），`--quiet`；
- EdgeGate `least_conn`，3 个后端，`access_log=off`，`log_level=warn`，健康检查 5 s；
- `eg_loadgen` 固定连接数、HTTP/1.1 keep-alive，每连接请求数 = 100000 / 连接数；
- 每种配置 3 轮，表中取中位数；
- 直连测试只连 app-a；代理测试使用 3 个后端，二者不是“只差一层代理”的严格对照，但能看出单事件循环的成本；
- 大文件：3 次 64 MiB 下载，1 连接；
- 慢客户端：4 MiB 响应，客户端 16 KiB / 20 ms，同时每 200 ms 抓 `/metrics`。

复跑：

```bash
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-release -j
bash scripts/bench.sh
```

原始输出：[`benchmark-raw.txt`](benchmark-raw.txt)。

## 小 JSON（`GET /api/info`）

每轮 100,000 请求，3 轮：

| 连接数 | 直连 QPS（中位） | 代理 QPS（中位） | 直连 P50 / P99 | 代理 P50 / P99 |
| --- | --- | --- | --- | --- |
| 1 | 24,525 | 9,134 | 0.035 / 0.119 ms | 0.086 / 0.374 ms |
| 8 | 383,866 | 25,901 | 0.015 / 0.054 ms | 0.284 / 0.612 ms |
| 32 | 357,631 | 28,238 | 0.069 / 0.230 ms | 1.024 / 3.368 ms |

原始范围：

- 直连 8 连接：314,321–416,293 QPS；
- 代理 8 连接：25,719–26,560 QPS；
- 代理 32 连接：28,217–29,590 QPS。

### 解读

- 1 连接时是请求-响应往返，压测器每线程一次只有一个在途请求；代理比直连多一次完整解析/转发/重新分帧，因此 9.1k vs 24.5k。
- 8/32 连接时，直连后端可以同时服务多个压测线程；EdgeGate 是单个 epoll 线程，QPS 上限约为 2.6–3.0 万。增加连接数只增加了并发排队，P99 从 0.6 ms 升到 3.4 ms。
- 这不是“代理无用”：代理提供连接池、健康检查、重试、可观测性和统一入口；代价是单核解析/复制/状态机成本。
- 进一步优化方向：多 worker + SO_REUSEPORT、减少每请求分配、批量 `send`/`recv`、异步日志、更轻的指标更新。v1 没有做，以免把范围扩大到分布式状态共享。

## 64 MiB 下载

3 个请求，1 连接，每轮总字节 201,326,592：

| 路径 | 3 轮耗时 | 等效吞吐 |
| --- | --- | --- |
| 直连 | 0.095 / 0.062 / 0.064 s | 2.1–3.2 GB/s |
| 经代理 | 0.066 / 0.057 / 0.057 s | 3.0–3.5 GB/s |

这是 loopback + 页缓存，不代表磁盘/公网吞吐。它验证的是：大响应是流式转发的，代理没有把 64 MiB 整包读进内存；慢客户端测试进一步证明缓冲会被水位限制。

## 慢客户端背压

| 指标 | 结果 |
| --- | --- |
| 响应大小 | 4 MiB |
| 客户端读取 | 16 KiB / 20 ms |
| 应用层缓冲峰值 | 262,144 B（正好等于高水位） |
| 上游读暂停次数 | 15–30（不同运行） |
| 进程 RSS | 5.6–7.9 MiB |

输出示例：

```text
bp: received=798720/4194304 reads=50 buffered=262144 pauses=11 resumes=10
bp: received=1593344/4194304 reads=100 buffered=262144 pauses=14 resumes=13
backpressure: buffered<=262144B pauses=15 rss=5652KiB
```

## 故障转移 / 重试

不是性能数字，但属于验收：

- 杀掉一个后端后，健康检查在 300 ms 间隔 + 200 ms 超时 + 阈值 1 的条件下摘除；请求只落到剩余实例；
- 重启后端后约 1.5 s 内恢复派发；
- flaky 上游：GET 重试成功，POST 返回 502 且不重试；
- 全部 drain 后返回 503；enable 后恢复 200。

详见 [`manual-test-report.md`](manual-test-report.md) 与集成测试。

## 局限性

1. WSL2 虚拟化、未绑核，单次运行方差较大；正式结论应多轮取中位数并记录环境。
2. 直连与代理的后端数量不同（1 vs 3），不是严格的单变量对照。
3. `/api/info` 响应很小，主要测请求路径开销；大文件测试主要测流式吞吐，二者不能互相替代。
4. `eg_loadgen` 每个连接串行请求，没有测 HTTP pipelining；代理本身支持延迟处理的管线化，但未做吞吐基准。
5. 没有测 TLS/HTTP2，因为 v1 不支持。
